# MTP draft stream priority screen

**Decision: keep the draft stream at the default priority on gfx1100.** `STRATA_MTP_HIP_PRIO=1` improved Chinese dual in all three pairs but regressed Chinese single in two of three, with both code lanes flat. Not a clear all-lane win; the switch stays off in the template and the engine default for this GPU is unchanged.

## Mechanism and why this was tested

ROCm hands out hardware queues per priority level (`GPU_MAX_HW_QUEUES` per level). With the draft stream raised to the highest priority it gets a queue of its own, so a draft round no longer waits behind the commit graph the verifier's stream launched just before it. The same switch is default-on for gfx1200/gfx1201, where upstream measured draft wall time 5.8 → 3.5 ms per window on an R9700. On this dual-gfx1100 rig the development engine keeps verification and the MTP chain on CUDA1 behind three hardware queues, which the earlier analysis flagged as an untested contention hypothesis.

A live probe against the running production service confirmed the priority range on both cards (`hipDeviceGetStreamPriorityRange` → 1..-1, two discrete levels), so the mechanism is available. The test binary adds one diagnostic `fprintf` to `mtp.cpp` that reports whether the priority was applied and the queried range; it prints only when the switch is set and changes no behavior.

## Method

Binary `528530d9…` (the adopted fixed-zero PCIe graph patch plus that log line), same weights, profile seed, power caps, prompts, penalties and cache policy as the two campaigns before it. Three fresh-load pairs (base, mp / mp, base / base, mp; pair 2 reversed task order), 1,024 output tokens per request. Two frozen loads (adaptation and suffix drafting off) checked serial, repeated-serial, pipelined and forced-rollback texts at 384 tokens. All 36 scored requests reached full budget. Every `mp` load logged `strata mtp: draft stream priority raised (range 1..-1)`; the base loads logged no priority line.

## Frozen parity

Both arms produced byte-identical serial, repeated-serial, pipelined and forced-rollback texts, identical between arms (SHA-256 `34e47874…` and `78b1040e…`, matching the previous campaign's frozen arms). Stream priority is scheduling only and that held.

## Frozen per-window measurement

The frozen loads turned out to be deterministic on this rig: independent loads of the same arm reproduce the window count, the rollback count and the total wall time to the millisecond (locked power caps), so frozen-arm differences are exact rather than sampled. Against the base arm, the priority arm costs **+1.08 ± 0.07 ms per window on every frozen request** (Chinese piped/forced 18.07→19.11 and 19.42→20.53; code 17.32→18.49 and 18.26→19.27). Raising the draft stream's priority measurably slows the solo decode path on CUDA1 — consistent with the Chinese-single regression in the scored pairs — while the batch path (two slots) gains. This exonerates draft-queue contention as a cause of the remaining solo-lane gap.

## Notes

- The first campaign attempt aborted on its own assertion before scoring: the prepared `mp` arms still carried `STRATA_MTP_HIP_PRIO` in their `env_del` list, so the runner deleted the variable it had just set and the engine never raised the priority. Production was restored automatically; the corrected run is recorded here.
- Together with the look-ahead screen this is the second scheduling-only switch that consistently helps Chinese dual on this rig and does not help (or hurts) Chinese single. Per-load numbers are in the [structured record](2026-11-20-mtp-prio.json).
- Production 0.1.43 was restored and verified loaded after both attempts; the configuration hash was unchanged, the test port was closed, and no monitor faults occurred.
