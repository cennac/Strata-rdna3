## The reference mismatch, chased to one line

The first validation run was aborted by design: all 14 raw and 12 sampled probes were internally consistent, but the Chinese probes diverged from the pinned 0.2.16-dev reference at generated token 7–8 (the code probes matched all 96 tokens; forced rolls 30/22 vs 32/23). Six measured bisect cycles isolated the cause:

| Cycle | Reverted to 0.2.16 | Result |
|---|---|---|
| b442-r2 | the rope HIP rounding hunk alone | same signature — rope excluded (tokens byte-equal to the full build) |
| bisect1 | all 10 changed GPU kernel files | same signature — kernels excluded |
| bisect2 | prefill compute trio | (compile-blocked by API coupling; the sorts were later verified env-off) |
| bisect3 | b437's expert_source restructure | same signature — our own line excluded |
| bisect4/5 | verify.cpp + mtp.cpp, then generate.cpp alone | **generate.cpp alone reproduces the 0.2.16 reference bitwise** |
| bisect6 | ONE line of generate.cpp | **matches: the reference is reproduced** |

The line is upstream #6110: `const bool trim = o.trim_stage_weights && multi_gpu && !stages.empty() && !stage_trim;`. 0.2.16 trims stage weights twice on a two-card split; 0.2.17 skips the second pass. With `--trim-stage-weights` set (this template), the fix changes what the cards trim, hence the residency/layout the run starts with, hence which experts the CPU computes — a legitimate, intentional engine 0.1.63 behavior change, not a merge defect: with that single line restored to 0.2.16 the entire integration is **bit-identical** to the adopted baseline (14 raw + 12 sampled probes, forced rolls 32/23).
